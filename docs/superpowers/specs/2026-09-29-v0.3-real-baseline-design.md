## 目标

在 arm64 物理设备上建立可信性能基线：功耗（tokens/Joule）、温度节流、内存分解随逐 token 指标同钟对齐，产出"prompt 长度 × 线程数"矩阵报告（CSV/JSON），并完成 v0.2 遗留清理。

## 范围（6 项）

1. **平台采集层**：`core` 新增 `PlatformSampler`（功耗/温度/内存/CPU 四 reader + 能力自检矩阵）
2. **采集线程落地**：`MetricsCollector::Impl::collectionLoop`（现为 TODO 空转）接入 sampler，窗口化时间线导出
3. **基线矩阵 harness**：新"基线"Tab，内置 prompt 集 × 线程数矩阵，一键跑完、逐 cell 导出
4. **导出与接线**：CSV（一行一 cell）+ JSON（cell 全时间线）+ meta.json；`PowerChart` 接真实曲线（补 v0.2 占位）
5. **校验脚本**：`scripts/xcheck_power.sh`（adb 侧电流积分对照 app 读数，验证交付物，不进产品代码）+ 首轮真机会话同时补跑 v0.2 operator checkpoint 清单
6. **v0.2 挂账清理卡**：N2/N3/N4、R5、T6b（详见 ⑤）

不在本版范围：SQLite 持久化导出（导出由 Kotlin 完成）、GPU/NPU 利用率%、Python 分析、Android 14 Thermal API headroom（sysfs 为主通道）、模型下载管理（v1.0）、KV cache 持久化（v0.4）、推测解码（v0.5）。

## ① PlatformSampler（`core/include/edgepilot/platform/platform_sampler.h` + `core/src/platform/platform_sampler.cpp`）

```cpp
enum class SamplerStatus { OK, PERM_DENIED, ABSENT };

struct Capability {            // probe() 结果，全程只读
    SamplerStatus power, thermal, mem, cpu;
    std::string power_path;    // 实际命中的 supply 节点（如 /sys/class/power_supply/battery）
    std::vector<std::string> cpu_zone_types;  // 命中为 CPU 类的 thermal_zone
};

struct PowerSample   { double t_ms; double power_mw; };   // |current_µA| × voltage_µV / 10⁹ → mW
struct ThermalSample { double t_ms; float cpu_max_c; };
struct MemSample     { double t_ms; size_t pss_kb, vmrss_kb; };

class PlatformSampler {
public:
    bool probe();                       // 启动时自检一次；缺权限走降级，不抛异常不崩
    const Capability& capability() const;
    bool readPower(PowerSample& out);    // 返回 false = 能力不可用
    bool readThermal(ThermalSample& out);
    bool readMem(MemSample& out);
};
```

读取源与语义：

- **功耗**：`/sys/class/power_supply/<battery>/current_now`（µA，放电为负，取绝对值）× `voltage_now`（µV）。目录名运行时探测（`battery` → `bcma_battery` 等备选，枚举 `/sys/class/power_supply/*/type==Battery`）。电压读数异常（≤0 或 >20V）→ 该样本作废不并入。
- **温度**：枚举 `/sys/class/thermal/thermal_zone*/type`，命中含 `cpu|cpufreq|llama|cluster|gpu`（大小写不敏感，骁龙常见 `cpu-ns0`/`gpufreq*`）的 zone，取 `temp`（毫度→℃），一次读取得 CPU 簇最大值；无命中 zone → `thermal=ABSENT`。
- **内存**：`/proc/self/smaps_rollup` 的 `Pss:` 与 `/proc/self/status` 的 `VmRSS:`（KB）。恒可读（自身进程）。
- **CPU**：`/proc/stat`（本版仅采样占位，不进导出列）。
- 非 Android 宿主（桌面调试构建）：`probe()` 全部 `ABSENT`，`read*` 恒 false——core 不得有 Android 硬依赖（`<android/log.h>` 仅 `__ANDROID__` 内，沿用 log.h 模式）。

## ② MetricsCollector 采集线程接入

- `MetricsCollector::Config.sample_interval_ms` 默认 100（10Hz）。
- `collectionLoop`：每 tick 调 sampler 三读，按 `t_ms` 追加进当前活动窗口缓冲；**能力不可用的通道不产生样本**（缓冲留空，导出侧空列/`unavailable` 注记，绝不补 0——v0.2 纪律延续）。
- 新增窗口 API（`start`/`stop` 之外）：
  ```cpp
  void beginWindow();                                   // 清空缓冲、开窗
  std::string endWindowJson();                          // {"power":[[t,mw]...],"thermal":[[t,c]...],"mem":[[t,pss_kb,vmrss_kb]...],"n":{"power":N,...}}
  ```
  缓冲加锁（采集线程写、JNI 线程读），容量上限 20 000 样本/通道（约 33 分钟），越界丢最旧。
- 生命周期：`core/src/jni/edgepilot_jni.cpp` 持 `static MetricsCollector g_metrics;`，JNI 面新增：
  - `nativeSamplerProbe(): String` → 能力矩阵 JSON（UI 显示采集可用性徽标）
  - `nativeSamplerBegin()` / `nativeSamplerEnd(): String` → 开窗/收窗
  - `nativeInit(modelPath, threads)`：**签名扩展**（`jint threads`，`0`=沿用 `getRecommendedConfig`）；矩阵每换线程数重载模型（TinyLlama 秒级重载，可接受）。Kotlin `NativeEngine.init(modelPath, threads = 0)` 保持默认兼容。
- `InferenceRecord` 资源字段（`power_avg_mw` 等）本版**不**填充——聚合在 Kotlin 侧由窗口 JSON 计算，避免双实现漂移（ledger 记此裁定）。

## ③ 基线矩阵 harness（新"基线"Tab）

```
MainApp NavigationBar: 测试 | 指标 | 基线(新)
BaselineScreen
  ├─ 配置区：线程集多选(默认 2/4/8)、每 cell maxTokens(默认 128)、重复次数(默认 1)
  ├─ 「跑完整矩阵」→ BenchmarkSuiteRunner
  └─ 进度/日志区 + 完成后导出路径 + 单元格结果表(可滚动)
```

- **内置 prompt 集**（`BenchmarkSuiteRunner` 常量表，英文——TinyLlama 英文 tokenizer；`[短/中/长]` 分桶，全文即 spec 定稿，计划原样搬运）：
  - 短（6 词）：
    `Explain gravity in one sentence.`
  - 中（≈60 词）：
    `You are a physics tutor. A student asks: "Why does a feather fall slower than a hammer on Earth, but both land together on the Moon?" Explain the role of air resistance and gravity step by step, then give one everyday example that shows the same principle, and finish with a short check question for the student to answer.`
  - 长（≈250 词，摘要请求内嵌全文）：
    `Please summarize the following article in two sentences:` + 一段关于手机 SoC 热节制的文章（"Modern smartphone processors are examples of carefully negotiated compromise between performance, battery life, and heat. A laptop or desktop chip may draw tens or hundreds of watts because a heatsink and fan carry the heat away. A phone has no fan. Its metal frame and glass back are the cooling system, and they can only shed so much heat before the surface becomes uncomfortable to hold. When the silicon gets too hot, the power management firmware lowers the clock frequency of the CPU and GPU cores. This process, called thermal throttling, protects the hardware but makes everything slower. Users notice it most during long gaming sessions, video recording, and lately, during on-device artificial intelligence workloads such as running a large language model locally. These workloads stress many cores continuously, which is exactly the pattern that produces heat fastest. Manufacturers handle the tension differently. Some allow brief bursts of very high speed followed by a long cooldown, while others hold a lower but steadier frequency for as long as the workload continues. Benchmark numbers published at launch usually measure only the first burst, which is why real-world sustained performance is often lower than advertised. Measuring a phone fairly therefore means watching not just speed, but how speed changes as the device warms up, how much energy each useful computation costs, and whether the machine can keep going without shutting down."）
  - 三桶 prompt 字符数写入导出（`prompt_chars` 列），长桶必须足以区分 prefill 时长。
- **Runner 流程**（`viewModelScope.launch(Dispatchers.Default)`，逐 cell 串行）：
  1. `init(modelPath, threads)` → 2. `samplerBegin()` → 3. `generateStream(...)`（阻塞至 `onDone`）→ 4. `samplerEnd()` 取窗口 JSON → 5. 聚合 cell：`energy_J = Σ mw·Δt / 1000`（样本间隔取实际 t_ms 差，首末各半窗）、`avg/peak_mW`、`tokens_per_joule = total_tokens / energy_J`、`temp_start/peak_c`、`pss_peak_mb`、`power_source = capability.power`、`status = OK|ERROR`
  6. UI 进度行；失败 cell 记 ERROR 继续（N4 联动：`total_tokens==0 && text` 前缀 `[错误]` → `status=ERROR`，不伪装 0 值成功）。
- 矩阵中任一 `init` 失败 → 该线程列全 ERROR；生成崩溃属不可恢复 → 停跑、保已有导出。

## ④ 导出与 UI 接线

- 目录：`getExternalFilesDir("bench")/<yyyyMMdd_HHmmss>/`（app 专属外部目录，免权限，`adb pull` 直接可达）：
  - `bench.csv`：表头 `run_ts,device,android_soc,threads,bucket,prompt_chars,max_tokens,total_tokens,ttft_ms,itl_p50_ms,itl_p90_ms,itl_p99_ms,tokens_per_sec,energy_J,avg_power_mw,peak_power_mW,tokens_per_joule,temp_start_c,temp_peak_c,pss_peak_mb,power_source,thermal_source,status`；`device/android_soc` 取 `Build.SOC_MODEL/Build.SOC_MANUFACTURER`（API31+，缺则 `Build.MODEL`）

- **降级 UI**：基线 Tab 顶部徽标行：`功耗⚠不可读 / 温度⚠无zone / 内存✓`（probe JSON 驱动），不可用列导出留空。

## ⑥ 校验脚本（验证交付物）

`scripts/xcheck_power.sh`（git-bash 可跑；adb 全路径可覆盖）：

```
用法: xcheck_power.sh <秒数> [adb路径]
行为: adb shell 枚举 /sys/class/power_supply/*/type==Battery，
     以 5Hz 采 current_now×voltage_now → 积分 → 打印 avg_mW/energy_mWh；
     同时打印 dumpsys battery 摘录（voltage/current 对照）
     与 bench.csv 某 cell 的 avg_power_mw/energy_J 人工对比
```

真机 SELinux 若连 adb shell 也拒绝 `current_now`，脚本输出 `PERM` 并提示改用 `dumpsys batterystats` 手算——此时 app 侧 `power_source=PERM_DENIED` 属预期降级，验收标准 2 以 batterystats 口径判。

## 验收标准

1. 真机跑完整矩阵（3 prompt × 线程 {2,4,8}，maxTokens=128）无崩溃，`bench.csv` 每行数值可追溯到一次真实运行，`adb pull` 成功
2. `tokens_per_joule` 计算成立且 >0；app 侧 `avg_power_mW` 与 `xcheck_power.sh` 同窗（≥60s）积分偏差 ≤±30%（瞬时采样 vs 电化学积分容差；batterystats 口径同判）
3. 温度时间线随连续运行上升、桶间回落肉眼可见；峰值写入 CSV
4. PSS 峰值曲线合理（加载后跳变≈权重级、推理中缓升含 KV）；权重+KV+其它与 PSS 总和对账 ±15% 内（权重取 GGUF 文件 size，KV 取 `getKVCacheInfo().used_memory_bytes`）
5. v0.2 全部 checkpoint（打字机/停止/分位数/日志静默/转义/瀑布柱数）真机一次过；N4 错误（超长 prompt）在 UI 有显式错误而非 0 值假成功
6. 能力任一通道 `PERM_DENIED/ABSENT` 时：对应列留空 + 徽标提示，其余列正常产出（无补 0、无崩溃）
