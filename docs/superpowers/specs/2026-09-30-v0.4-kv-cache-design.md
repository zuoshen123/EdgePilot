# EdgePilot v0.4 — KV Cache 与 Prompt Cache 设计（Spec）

日期：2026-09-30 · 状态：草案（待用户复核）
承接：v0.3 spec `2026-09-29-v0.3-real-baseline-design.md`（全局约束、测量基建、红线全部沿用）

用户裁定（2026-09-30 头脑风暴四问）：
① 范围=四项全做，推荐器做薄（规则+卡片，半天量级）
② 多轮载体=矩阵 harness 会话桶 + 测试 Tab"多轮"开关，不建聊天 Tab
③ 持久化=API + 跨进程验证（不建存档 UI），指纹不匹配拒绝导入
④ 量化=创建时开关（type_k/type_v），compressKVCache 定义为重建语义；验收按 KVCacheInfo 字节口径，PSS 如实报告

与口头设计的一处差异（复核时可推翻）：持久化容器由"EPKV1 自研二进制头"改为 **llama.cpp 原生 kvdat 文件 + JSON sidecar**。理由：`llama_state_seq_save_file` 自带版本与长度校验且直接写文件路径，自研头无法前置只能造二次容器——sidecar 方案保证同等（实际更强：adb pull 肉眼可验）的"模型指纹校验、不匹配拒绝"契约，少一段自定义二进制格式的实现与评审面。

## 0. 目标与非目标

**目标**（ROADMAP v0.4 全兑现）：
1. Session 化多轮对话：KV 跨轮复用、增量 prefill，cache on/off TTFT 量化对比。
2. KV 持久化：`exportKVCache/importKVCache`（inference_backend.h:73-76 现 stub）落地为文件级会话保存/热恢复。
3. KV 量化：`ModelConfig.kv_cache_bits`（types.h:67，现恒 16 未消费）生效——F16/Q8V8/Q8V4 三档创建时映射 `llama_context_params.type_k/type_v`；`compressKVCache` 兑现为重建语义。
4. 配置推荐器：`getRecommendedConfig`（backend_factory.cpp:61-88）三档 RAM 规则之上补 KV 内存预算校验，硬件区一张"推荐配置卡片"+一键应用。

**验收标准**（真机 arm64 实测，未验不 ✅）：
- **V1** 多轮 TTFT：矩阵会话桶 3 轮脚本，`cache_on` 第 2/3 轮 TTFT 相对 `cache_off` 同轮，**中/长桶降幅 ≥70%**（短桶如实报告不设门槛）。
- **V2** 长上下文内存：同一 cell（n_ctx=4096、灌 ~3.5K token）`used_memory_bytes` **Q8V4 对 F16 降幅 ≥40%**（理论 ≈-59%，见 §4 公式）；PSS 降幅（预期 ~-33%）用 v0.3 采样器如实报告，不设达标线。
- **V3** 会话热恢复：跑 ≥2 轮→导出→`am force-stop`→冷启动→加载同模型→导入→**贪心（temp=0）续写前 32 token 与中止前基线完全一致**；对指纹不匹配的存档导入必须拒绝并显式报错（不假恢复）。
- **V4** 推荐卡片：规则渲染正确，"应用"后加载实际采用推荐值（日志/CSV 可证）。
- **V5**（抽检，不设门槛）：Q8V4 对 F16 同 prompt 贪心前 32 token 一致率如实记录。

**非目标**（明示推迟）：多会话并发、聊天 Tab UI、KV 原地重量化（llama.cpp 无此 API）、滑动窗口/驱逐、SWA 部分态、defrag、`prefill/verifyTokens` 等投机采样接口（属 v0.5）。

## 1. 会话与增量 prefill（核心语义）

### 1.1 概念

会话态 = KV cache 当前内容本身，**不引入独立 session 对象**。生成请求携带 `continueSession` 标志：

- `continueSession=false`（默认，= v0.3 行为逐字不变）：`resetKVCache()` + 全量 prefill + BOS（现状 ggml_backend.cpp:220-228 / 307-320 双路径）。
- `continueSession=true`：**跳过 reset**；本轮 tokenize **仅新输入文本**（`add_bos=false`）；prefill 增量 token 后解码。assistant 上一轮生成的 token 本就在 KV 中，不重放。
- "结束会话" = 下一次生成不带 `continueSession`（自动清重装）；模型重载/`clearKVCache` 同样终结。

`GenerateRequest`（types.h:72-85）新增 `bool continue_session = false;`——默认值保全所有既有调用点行为（v0.3 矩阵/单跑零变化）。

### 1.2 多轮内容组装

每轮 Kotlin 侧只传**用户新消息文本**；角色模板胶水由 **native 侧**在 `continue_session=true` 分支执行（`llama_chat_apply_template` 是 C 层 API，Kotlin 拿不到）：tokenize 前先拼一条 `user` 消息 + 尾部 `assistant` 开场（GGUF chat template 存在时；TinyLlama 有），历史不重复提交（KV 即历史）。无模板模型退化为裸文本 `\n用户: X\n助手:` 胶水并日志注明——**演示玩具级，测量真实**：本框架卖点是 TTFT 差值不是聊天质量。

### 1.3 越界与错误

- 增量 prefill 超出剩余 n_ctx → 走 N4 既有 `[错误] prefill 失败（可能超出上下文）` 链（`totalTokens==0` 门、UI ERROR、CSV error cell），不静默截断不驱逐。
- 会话中 `load_model`（同路径同线程 fast-path 除外）与 `nativeRelease` 都终结会话（KV 随 ctx 消亡），KDoc 写明。

## 2. 持久化：导出/导入与会话存档

### 2.1 文件对（容器决定见页首差异说明）

- `<name>.kvdat`：`llama_state_seq_save_file(ctx, path, /*seq_id=*/0, tokens, n_token_count)` 原生格式（自带版本号+状态长度校验；tokens 数组由后端在会话期间记录的 token 历史提供——`Impl` 新增 `std::vector<llama_token> session_tokens`，reset 时清空、每轮 prefill/生成追加）。
- `<name>.kvdat.json` sidecar（native 直接 fprintf 手写固定字段，不引 JSON 库）：`schema:"epkv1"`, `model_path`, `model_size_bytes`（GGUF stat）, `n_ctx`, `kv_bits`, `n_tokens`, `saved_at_ms`（steady 域不用，墙钟仅备注字段不参与校验）。

### 2.2 导入校验顺序（全部不过即拒绝，返回 false + EP_LOGE 原因）

1. 两文件存在且可读；
2. sidecar 可解析且 `schema=="epkv1"`；
3. **模型指纹**：`model_path` 与当前加载一致 **且** `model_size_bytes` 与当前 GGUF stat 一致（防路径不变文件被换）；
4. `kv_bits` 与当前 context 一致（llama 数据布局随 type_k/v 变，混档导入必坏）；
5. `llama_state_seq_load_file` 返回 0 → 拒绝（原生校验兜底：版本/长度/容量）。
成功后：`impl_->resetKVCache()` 先行清场 → 装载 → `n_past = loaded_token_count`、`session_tokens` 替换为装载 token 数组 → 后续轮 `continueSession=true` 自然续写。

### 2.3 跨进程热恢复通道（无 UI，adb 驱动）

- 导出：`adb shell am start -n com.edgepilot/.MainActivity --es ep_session_save <基线导出目录内文件名>`；VM 冷启动序列 = 加载默认模型（路径沿用上次设置不可用则日志报错终止）→ 会话跑内置"恢复校验脚本"（两段用户消息，temp=0，maxTokens=32）→ **导出前把 32 token 基线续写结果写入 sidecar 目录的 `replay_baseline.txt`** → `ep_session_save` 落文件 → finish 日志。
- 恢复：`--es ep_session_load <路径>` → 冷启动加载模型 → 导入 → **续写同参贪心 32 token** → 与 `replay_baseline.txt` 比对 → 逐字一致则日志/`session_recover_result.txt` 写 `PASS`，否则 `MISMATCH`（如实记录，不重试不掩盖）→ 任何校验步失败写 `REJECTED: <原因>`。
- 验收 V3 即走此通道 `am force-stop` 前后两轮。（此机制同时是 T9-未完成的真机会话新增清单项。）
- 贪心前置：现采样链固定 temp=0.8（ggml_backend Impl::buildSampler），`GenerateRequest.temperature` 无人消费。T1 落地"temp≤0 → `llama_sampler_init_greedy` 链（逐次构建即用即释）"，否则 temp=0 只是装饰，V3 一致性无从谈起。

### 2.4 接口兑现

`InferenceBackend::exportKVCache()/importKVCache(bytes)`（:73-76）用 `llama_state_seq_get_data/set_data` 缓冲版**实现为真**（供未来非文件消费者）；但 **JNI 只暴露文件路径版**（数百 MB 不进 JNI 字节拷贝）。`clearKVCache` 已有实现不动。

| 新增/变更 | 签名 | 说明 |
|---|---|---|
| `nativeInit` **扩展** | `(String,I) → (String,II)` 第三参 `kvBits` | 16/8/4；非法值回 16 并日志；Mock 分支同步参 |

| `nativeSetKvQuant(bits)` | `(I)Z` | `compressKVCache` 的 JNI 皮：重建 ctx（同模型新 type_k/v），**清空 KV**，true=已切换；KDoc 明示"历史需重灌" |

## 4. 量化：三档映射与字节账

创建时映射（`loadModel` 构 `llama_context_params` 处）：

| kv_bits | type_k | type_v | 每 token 字节（K+V 合计） |
|---|---|---|---|
| 16 | F16 | F16 | `2·L·Hkv·D·2B`（现状公式，getKVCacheInfo:500-502） |
| 8 | Q8_0 | Q8_0 | `2·L·Hkv·(D·1B + D/32·2B)` |
| 4 | Q8_0 | Q4_0 | `L·Hkv·(D·1B + D/32·2B) + L·Hkv·(D/2 + D/32·2B)` |

（L=层、Hkv=kv 头、D=head_dim；Q8_0 块=32元素 34B、Q4_0 块=32元素 18B。TinyLlama 22×32×64：F16=180,224 B/tok；Q8V8=2·704·(64+4)=95,744；Q8V4=704·(68+36)=73,216 → **-59% 对 ≥40% 门槛，余量 19pt**。）

- **K 保守取 Q8**（业界共识 K 对量化敏感；用户裁定已含）。V 的 Q4_0。
- `getKVCacheInfo` 的 per_tok 从硬编码 F16 改为**按当前 ctx 实际 type 计算**（读回 cparams 记录值，不猜）。
- 质量抽检 V5：贪心 token 一致率（temp=0 消采样噪声；贪心对量化偏差敏感，恰是优点）。
- 4K cell 内存现实：Q4_K_M 权重 ~640MB + F16 KV 738MB ≈ 1.4GB 级 PSS——高端骁龙可行；加载 OOM 失败 → 该 cell ERROR（不伪造），runbook 注记。

## 5. 矩阵会话桶（V1 测量）与量化对比 cell（V2）

### 5.1 harness

`BenchmarkSuiteRunner` 新增 `runSessionSuite()`：3 段脚本（短≈40t/中≈220t/长≈560t 首轮）× 每段 3 轮 × {cache_off, cache_on} × 线程集沿用当前选择（默认推荐）。cache_off：每轮全重装（含重放累积历史文本）；cache_on：§1 增量。**同一 cell 对**才可比：轮 2/3 的 TTFT 逐轮配对。

导出**新文件 `session.csv`**（v0.3 `bench.csv` 23 列 schema 冻结不动，保 xcheck 兼容）：`run_ts,soc,bucket,turn,cache_mode,threads,ttft_ms,itl_p99_ms,total_tokens,tokens_per_sec,energy_j,cache_hit`（`cache_hit = 1-turn重放token/本轮总token`，诊断列）。JSON 镜像同字段。`BaselineScreen` 加第二按钮"跑会话矩阵"，复用 running 互斥与导出提示。

### 5.2 量化对比

`runQuantCompare()`：固定长 prompt（~3.5K token 合成文，内置常量）灌入 n_ctx=4096（不足则按设备上限如实缩），按 {16,8,4}×{threads=推荐} 各 `init(kvBits)` 重建 → prefill 满 → 记录 `used_memory_bytes`+窗 PSS 峰值 → 贪心 32 token 存 `quant_tokens_<bits>.txt`（V5 比对源）→ 导出 `quant.csv`。`BaselineScreen` 第三按钮。三档同进程顺序跑（每档全新 init，无跨档状态泄漏）。

### 5.3 测试 Tab 多轮开关（裁定②演示层）

`HomeScreen` 增加"多轮会话"开关：
- 开：首轮以 `continueSession=false` 起会话，之后每次运行只提交**本轮新输入**（`continueSession=true`）；界面逐轮显示 TTFT（行列表，轮次可数）。
- 关 / 重载模型 / prefill 失败（N4 链）/ 引擎被释放 → 轮次归零，会话终结（§1.1 语义）。
- `runBenchmark(prompt, maxTokens, continueSession=false)` 透传 `NativeEngine.generateStream`；开关关闭时 v0.3 单跑行为逐字不变。

## 6. 配置推荐器（薄）

- 规则层（`getRecommendedConfig` 增强，仍纯函数）：现有三档 RAM→{ctx,batch,threads} 保留；新增 **KV 预算校验**：`predicted_kv = ctx × per_tok(F16) × 1.15(头/对齐裕量)`，若 `predicted_kv > available_bytes × 0.55` 则 ctx 逐档降（4096→2048→1024→512）直至满足；`kv_bits` 建议 = **质量优先**：默认 16，仅当 ctx 已降至 512 而 F16 KV 仍超预算时建议 8，8 仍超则 4；512×Q8V4 仍超 → 卡片如实显示"内存不足以安全跑长上下文"警示，不给超预算配置（规则有终止态，无解情形可见）。设备无"当前加载模型"概念则卡片只给推理建议，不做模型推荐（YAGNI）。
- UI 层：硬件 Tab（HomeScreen 信息卡下）**RecommendationCard**：三行（context/线程/KV 量化）+ 依据一行（RAM 数）+ **应用**按钮 → VM 记入 override，`loadModel` 路径透传 `init(path, threads=rec, kvBits=rec)`；日志"已应用推荐配置"。未点应用一切如旧。
- 纯展示+一次性 flag，无新持久层。

## 8. 风险登记

1. **llama_state_seq 版本漂移**：save/load 的 vN 格式随 vendored llama.cpp 变；sidecar 不锁 llama 版本字段——接受（同 app 同 .so 自洽），跨 app 版本恢复非目标。
2. **session_tokens 内存**：长会话 token 历史 vector（4K×4B=16KB 级）可忽略；但 save_file 需全量传指针——OK。
3. **chat template 缺位模型**：退化胶水已定义；矩阵三桶脚本本身无模板依赖（v0.3 原样）。
4. **Q4V 对部分模型劣化超预期**：V5 抽检暴露真数据，无门槛；如需回退改三档为两档属参数级改动。
5. **4K cell OOM（低端）**：ERROR cell 如实；验收设备为高端骁龙（用户确认）无碍。
6. **am start intent 通道**：`onNewIntent` 冷/热启动两路都要接（VM 一次性消费标志防重放）。
